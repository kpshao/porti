# 收缩旧五类模型，三层词汇成为唯一模型

ADR-0004 落地了三层分类（账本大类 / 产品形态 / 配置桶），但 schema v4 到 v5 期间旧五类字段、旧目标表与运行时兼容映射仍与最终模型并存，供迁移中的页面读取。收缩票把所有消费者迁移完成后删除这层契约：schema v6 删除 `funds.category` 与 `category_targets`，运行时不再有任何旧类别派生、兼容列写入或旧目标编辑路径；目标只存在于配置桶层（`bucket_targets`），基金分类只由 `ledger_category` / `product_form` / 权益系数字段表达。

旧分类目标在 v6 迁移中先剔除无对应产品形态的旧类别、其余归一化，再按固收+ 默认权益系数拆成三桶并直接写入 `bucket_targets`（用户已保存过三桶目标时保持原值），随后删除旧目标表与旧分类列；迁移前用 `VACUUM INTO` 留备份，清理步骤以「旧列 / 旧表是否仍存在」判定幂等。新库不再种子旧目标，三桶目标为空即「未配置」，偏离显示为空。

旧类别标签只保留在两处：导入器标签别名（继续接受旧 Excel 的类别列，`src/importer/labels.ts`）与历史迁移的冻结映射（`src/main/schemaMigration.ts`，只服务 v3 → v4 回填与 v5 → v6 旧目标折算）。其余代码、测试、验收脚本与文档一律使用三层词汇。拒绝的替代方案：继续保留兼容列（最终模型永远有两个事实来源，写入路径必须双写）；把旧目标折算留在读取层延迟进行（旧表永远删不掉，且「未确认」状态会无休止地出现在界面）；导入器直接拒绝旧标签（迫使用户重写历史 Excel，违背导入一次性迁移的承诺）。

**Consequences**: schema 版本为 v6；spec 原文写的「v5 清理迁移」因 v5 已被 `bucket_targets` 占用而顺延。迁移失败时调用方保留旧版本并下次重试，不再有读取层兼容兜底——旧结构只应由迁移处理，不参与常规读取。导入器是唯一仍识别旧标签的运行时路径；新增产品形态或分类字段时，需要同步 `CONTEXT.md`、本 ADR 与导入器别名表。新库从空目标开始，用户首次设置目标前不会看到伪造的偏离。
