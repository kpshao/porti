# 01: 概览持仓明细按大类分组

**What to build:** 计算引擎新增分组纯函数 `groupPositionsByCategory`（`CATEGORIES` 声明序骨架、空组剔除、非五值归入「其他」置底、组内基金代码升序、组头合计 = Σ `marketValue ?? 0`），由主进程在 `overview:data` 既有 handler 组装进契约；概览页持仓明细表改为「大类 / 大类市值」占最前两列并按组纵向合并单元格（`rowSpan` + 浅灰底 + 垂直居中），共 12 列；`computeCategoryComparison` 与 `selectCategoryTargets` 改为按 `CATEGORIES` 声明顺序输出，令持仓明细与大类配置对比两表同序。口径、宽度预算、接缝与测试落点详见 spec.md。

**Blocked by:** 无（依赖均为既有能力）

**Status:** resolved

- [x] 计算引擎：新增分组纯函数（`CATEGORIES` 骨架、空组不产生、非五值归入「其他」置底、组内基金代码升序、组头合计 `Σ marketValue ?? 0`、组内全 null 时合计为空值），按 spec「必测用例」补齐单测
- [x] 计算引擎：`computeCategoryComparison` 改为按 `CATEGORIES` 索引排序、非五值类目排在其后；`selectCategoryTargets` 去掉 `ORDER BY category`
- [x] 契约：`OverviewData` 承载分组结构，在 `overview:data` 既有 handler 组装（无新 IPC 通道，preload 与 `env.d.ts` 无需改）
- [x] 界面：12 列（大类 / 大类市值 / 代码 / 名称 / 份额 / 持仓成本 / 最新净值 / 市值 / 持仓盈亏 / 盈亏比例 / 年化收益率 / 目标金额（元））；前两列只在组内首行渲染并 `rowSpan` 合并；行内目标金额编辑与基金详情入口行为不变
- [x] 样式：新增 `.group-cell`（浅灰底 + 垂直居中）与 `.table-positions` 宽度收紧（内边距 10→6px、输入框 110→88px、组标签 `nowrap`），不动全局 `.table`
- [x] 验收：默认窗口宽度下无单元格折行；Σ 各大类市值 == 顶部总资产；同大类连续、无跨类穿插；空大类不出现
- [x] 导出：「持仓明细」小节保持平铺（含「大类」列、仍在第三列）不变；「大类配置对比」小节随 `computeCategoryComparison` 同步换序为 `CATEGORIES` 顺序
- [x] 零回归：既有测试全绿；交易流水、基金详情、收益统计、净值管理页不受影响

## Comments

- **设计取舍（grilling 结论）**：
  1. **大类市值独占一列，而不是塞进组标签或另设组头行**。最初 spec 曾设计"每条组头行 + 跨列合计"，但那让合计只能顶到表格最右缘、落在「目标金额（元）」列下方——而它求和的其实是「市值」列。改为「大类 / 大类市值」两个合并列后，合计有了自己的列，对齐问题消失。第一列只放类名，不承载数字。
  2. **组内按代码升序而非市值降序**。顺序跨刷新稳定、不随行情跳动，能形成肌肉记忆；且与导出「持仓明细」同向（同为代码升序），界面与导出在同一大类内部排序一致。代价是组内不再"市值最大的排最上"。此改动同时让"并列按代码升序 tie-break"与"市值缺失视为 0 排最后"两条规则失效并删除——代码是主键、不并列。
  3. **列名「大类市值」而非「总市值」**。「总市值」在本代码里已指全组合（`Totals.totalAssets` 的注释、界面卡片「总资产」），而"某大类的市值合计"的既有叫法就是「大类市值」（`types.ts` 的 `marketRatio` 注释）。避免一词两义。
  4. **不做表头排序**。持仓明细表当前完全没有排序，「点表头排序」是全新功能，且会岔出「组间是否按聚合值重排」等与本次目标无关的子树。另立 issue。
  5. **分组逻辑放引擎而非渲染层**。边界规则（脏值归入「其他」、空组剔除）是有对错的口径，与 `computeCategoryComparison` 里的处理同类；放引擎可用手算黄金值风格测掉，渲染层继续只做格式化。

- **两表同序的连带影响**：`exportService.ts` 复用同一个 `computeCategoryComparison`，故导出的「大类配置对比」小节会同步换序。已确认接受——界面与导出同序是本次意图，旧序本就是中文 UTF-8 字节序的副产物、无人选择过。

- **已知不一致（本次不治）**：「其他」组只存在于持仓明细表。对比表分组键是 `targets ∪ positions`，库中若真有脏值类目会照原样独占一行。根因是导入器识别不出类型时静默兜底成 `权益`（`src/importer/parse.ts`）且 `funds.category` 无 DB 级 CHECK 约束——另立数据处理 issue。

- **实施记录**（2026-09-22）：
  - **宽度预算是最容易翻车的一处**。12 列在默认窗口（1280，内容区约 1020px）下内容需求约 1090px，首版实现把基金名称挤成两行、「固守+」被断成「固守 / +」。修法：`.table-positions` 修饰类收紧横向内边距与输入框宽度，两列组标签 `nowrap`。窗口缩到 `minWidth` 960 时仍会折行，已明确接受为降级。**为避免再犯，端到端脚本新增「默认窗口宽度下无单元格折行」断言**（用 `Range` 量文本实际高度，超过 1.8 倍字号即判折行）。
  - **未预期改动**：`targetService.test.ts` 原断言 `selectCategoryTargets` 返回**字节序**（固守+/权益/流动性/纯债/黄金），注释亦写明「repo 按 category 排序（UTF-8 字节序）」。去掉 `ORDER BY` 后该顺序不再是契约，改为按大类名归一比较（`Object.fromEntries` + `toEqual`），并注明顺序归消费方负责。
  - **用例数**：新增 7 条单测（分组 6 条 + 对比表行序 1 条）；全量 188 测试绿，`npm run typecheck` 干净。
  - **导出换序未被既有用例区分**：`exportService.test.ts` 的种子库只有固守+/权益两个大类，二者在 `CATEGORIES` 声明序与旧字节序下顺序恰好相同，故该用例对行序变化不敏感（不构成回归证据）。行序本身由新增的 `computeCategoryComparison` 单测覆盖，导出经同一函数继承。
  - **端到端验收**：新增 `scripts/check-overview-grouping.mjs`（沿用 `check-fund-detail.mjs` 的 CDP 模式，零新依赖，另用系统 `sqlite3` 直读库作为独立事实来源）。真实库（10 基金 / 五大类）实测 GREEN，13 项断言全过；Σ 大类市值 936,241.33 vs 顶部总资产 936,241.32（1 分为各自独立舍入所致，在容差内）；console 无异常。
  - **回归**：`scripts/check-fund-detail.mjs` 实测 GREEN（该脚本从概览页 `.fund-link` 进入，正是被改动的 DOM 结构所在接缝）。
  - **真实库无脏值大类**（五个取值分布 4/2/1/2/1），故「其他」组在真实数据下未现身，仅由单测覆盖。单只基金的大类 `rowSpan=1`，同样只在真实数据下的「黄金」「流动性」两组可见。
