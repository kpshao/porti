# 收益合计与拆解可见（总收益卡 / 已实现盈亏 / 按笔追溯）

## Problem Statement

一次真实止损暴露的问题。用户在 2026-10-09 全清 `000217` 华安黄金ETF联接C（16032.86 份 @ 3.0370 = 48691.80 元，成本 59050 元），卖出已实现收益 **−10,358.20 元（−17.54%）**。概览页「落袋收益」卡片因此显示为负数，用户的第一反应是"这合理吗？为什么这样设计"。

**数值没有问题**——已用两个独立数据源查证：该基金 2013 年成立以来从未分红、从未份额折算，卖出端 3.0370 × 16032.86 = 48691.80 分毫不差。这是一笔真实的止损亏损（买点在 2026 年 1 月底金价冲顶期，卖在 10 月低位）。

问题全在**界面**——收益的加法关系从来没有被显示出来过：

1. **只有零件，没有和**。概览页 5 张卡（总资产 / 持仓盈亏 / 累计收益率 / 年化收益率 / 落袋收益）里有拆解体，却没有合起来的「总收益」。全仓库唯一输出总收益的地方是导出 Excel（`src/main/exportService.ts:74`），用户每次都得心算 `−7,026.89 + (−10,358.20) = −17,385.09`。
2. **名字骗人**。「落袋收益」的字面语义是"钱落进口袋"（暗示恒为正），实际语义是"已锁定盈亏"（可正可负）。止损场景下尤其别扭——「落袋为安」装不下「割肉」。
3. **无法追溯**。卖出后界面上没有任何地方说明"这一笔锁定了多少"——流水表卖出行不带已实现收益，用户只能看到概览那个累计数从 0 跳到 −10,358.20；卡区又是 3 张有色 2 张无色，负数更容易被视觉淹没。
4. **清仓后的残留**。清仓基金在持仓表里留下一行僵尸（市值/成本/盈亏全 0、比例 —），而它是全表唯一还记得这笔止损的地方；同时该大类的「实际投入比例」被算成 **1.15%**（因为 `净投入 = 59050 − 48691.80 = 10358.20`），在一只已清空的基金上凭空占着配置比例——黄金目标比例 5%，用户会看到一个永远消不掉的偏离。

## Solution

**一句话**：把「收益是怎么加起来的」变成界面上可见的事实。

1. **概览卡片区改两行版式**，补上「总收益」，让 `持仓盈亏 + 已实现盈亏 = 总收益` 肉眼可见。
2. **「落袋收益」改名「已实现盈亏」**，全部出口同步（概览 / 流水 / 基金详情 / 导出 / 图注 / CONTEXT.md / README）。
3. **已实现盈亏可按笔追溯**：流水表卖出行加「本笔已实现」列；卖出表单保存前实时预览本笔已实现。
4. **三张金额卡按正负着色**（总收益 / 持仓盈亏 / 已实现盈亏），红涨绿跌。
5. **清仓收尾**：持仓表默认隐藏零持仓（带「显示已清仓」开关）；大类「实际投入比例」按是否还有市值判定。

## User Stories

1. 作为投资者，我想在概览页一眼看到「总收益」，以便不用心算就知道整体赚亏多少。
2. 作为投资者，我想让 `持仓盈亏 + 已实现盈亏 = 总收益` 这个加法关系在界面上可见，以便看懂某个数字（尤其中间的负数）从哪来。
3. 作为投资者，我做止损后不想看到「落袋收益」这种暗示盈利的词，以便名字如实反映它可以是亏损。
4. 作为投资者，我想在流水表里看到每一笔卖出各自锁定了多少已实现收益，以便追溯概览那个累计数的来源。
5. 作为投资者，我想在保存卖出前就看到本笔的已实现收益，以便在唯一能反悔的时刻知道自己做了什么。
6. 作为投资者，我想让金额卡按正负着色，以便负数不会被视觉淹没（我最初的困惑正是没注意到那个负数）。
7. 作为投资者，我清仓一只基金后，不想让它在持仓表里留下一行 0/0/0/— 的僵尸，但仍想在需要时找回它的完整战绩与历史。
8. 作为投资者，我清空某个大类后，不希望它还在「实际投入比例」里占着一个凭空的份额。
9. 作为维护者，我想让「已实现盈亏」这个词在整个代码库和领域文档里只有一个写法，以便不出现新旧两套术语。

## Implementation Decisions

**引擎：合计与拆解的数据都已存在，不需要改口径。**

- `computeTotals` 已经返回 `totalReturn`（= 持仓盈亏 + 落袋收益）与 `realizedIncome`，概览页只是没消费 `totalReturn`。**本次零口径改动**。
- **新增**导出函数（如 `realizedPerSale(transactions): Map<txId, number>`），返回**每笔卖出**的已实现收益，供流水表列与卖出表单预览使用。推进逻辑必须复用 `applyCostBasis` 的同一套移动加权平均（`src/engine/compute.ts:46-85`），**不得另写一份口径**。
- `pnlClass` 目前在 `Overview.tsx:16` 与 `FundDetail.tsx:24` **重复定义**，本次抽到共用模块。这是 UI token 化之前的独立清理，不依赖 UI 改造。

**两行版式**（概览卡片区）：

```
第一行（结果）：总资产 | 总收益 | 累计收益率 | 年化收益率
第二行（分解）：持仓盈亏  +  已实现盈亏
```

第二行显式标出加法关系。第一行 4 张卡中，总收益 / 累计收益率 / 年化收益率 着色，总资产不着色（恒为正，着色无意义）。

**领域术语变更**（`CONTEXT.md:25-35`）：

- 「落袋收益」条目**改名为「已实现盈亏」**，正文 `一次落袋后` → `一次实现后`，旧名「落袋收益」与「落袋」一起进 `_Avoid_`。
- 「已实现收益」条目**保留**（单笔卖出口径），恒等式改写为 `Σ已实现收益 + Σ分红现金 = 已实现盈亏`，`_Avoid_` 补注「勿与『已实现盈亏』混用，后者含分红现金、口径更宽」。

⚠️ **措辞冲突（汇总时发现的最后一处，需用户点头）**：改名后「**已实现盈亏**」（累计，含分红）与既有的「**已实现收益**」（单笔卖出）只差一个字，而流水表新列装的正是单笔口径。若列也叫「已实现收益」，卡片与列名会在同一屏上撞车。**drop 决定**：流水表列名与卖出表单预览统一用「**本笔已实现**」，避开与「已实现收益」的近名，同时保留"这一笔"的限定语。

**清仓收尾**：

- `computePositions`（`src/engine/compute.ts:99-139`）继续返回零持仓基金（不删除，否则基金详情入口消失），由 UI 决定是否显示。
- 持仓表默认隐藏 `shares <= 0` 的行，顶部加「显示已清仓」开关。
- 大类「实际投入比例」：`investedRatio` 的分母/分子改为只统计**当前仍有市值**的持仓（`computeCategoryComparison`，`src/engine/compute.ts:223-229`）。已清空的大类记 0，不再显示凭空的偏离。

## Testing Decisions

- **好测试的标准**：只测函数输入 → 输出的外部行为（手算期望值），不测内部实现细节。
- **测试落点**：`src/engine/compute.test.ts`（新增 `realizedPerSale` 用例 + 大类比例用例）、`src/main/exportService.test.ts`（改名断言，数值不变）。
- **必测用例**：
  - `realizedPerSale`：单笔全清（期望 −10358.20 形态的手算值）；多次买入 + 部分卖出的移动加权口径；清仓后再买一笔卖出；同一基金多笔卖出的 id 归属正确。
  - 大类比例：某大类清仓后 `investedRatio` 记 0；混合持仓 + 清仓共存时分母正确。
- **恒等回归**：`computeTotals` 的 `totalReturn` 期望值全部不变（本次不碰口径）；既有 golden fixtures 全绿。
- **UI 断言**：改名的文案断言同步更新（`exportService.test.ts` 汇总行）。

## Out of Scope

- **已实现盈亏的时间维度聚合**（今年 / 本月卡片）。交易流水页已有现成的日期区间筛选（`Transactions.tsx:48` 的 `{ fundCode, type, from, to }`），加上「本笔已实现」列后用户可自行筛选。不够用时再在筛选结果下加一行合计，**不新增卡片区概念**——理由是「总资产」「持仓盈亏」是时点快照，往同一排卡片挂时间选择器会撕裂语义。
- **导入时的净值/日期数据体检**（校验净值与该日历史净值是否相符、标黄警告）。用户已明确说明其买入记录的净值是**多笔合并后反算的均价**，属有意为之，不做。
- **允许净值留空**（"我只知道总投入，不知道成交净值"的记法）。方向认可，本期不做。
- **跨基金的已实现明细列表**。基金详情已能逐只看。
- **零持仓基金的历史数据清理**。只做显示层隐藏，不动数据。
- **UI 整体风格改造**（抽 CSS token、配色、排版、形状质感）。该工作已单独挂起并有自己的预期（布局结构不动），本次两行版式是**信息架构**改动，与之正交、不合并。
